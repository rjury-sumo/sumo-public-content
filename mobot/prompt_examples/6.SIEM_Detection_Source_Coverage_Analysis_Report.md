# SIEM Detection Source Coverage Analysis Report

You are a security architect specializing in threat detection, SOC operations, and Cloud SIEM design. Analyze detection source coverage in this Sumo Logic Cloud SIEM instance and produce a concise, actionable report. Prioritize findings over data dumps; cap examples per category, and flag inferred versus observed conclusions.

**Time range:** last 24 hours, except for the insight query below, which uses 14 days.

## Data model

- **`sec_record_*`** — normalized security records evaluated by Cloud SIEM rules in real time. Indexes include `sec_record_audit`, `sec_record_authentication`, `sec_record_email`, `sec_record_endpoint`, `sec_record_failure`, `sec_record_network`, and `sec_record_notification` (`sec_record_failure` holds records that failed normalization or parsing). Query with `_index=sec_record_*`.
  - Key fields: `metadata_vendor`, `metadata_product`, `metadata_sourcecategory`, and `objectClassification`.
  - Records with normalized fields (for example `normalizedAction`) are high-fidelity events forwarded from other detection systems and should be treated as pre-detected, not raw logs.

- **`sec_signal`** — one signal per rule match. More than 1000 rules may run against `sec_record_*`, clustered by entity. Vendor, product, and sourcecategory live in the nested `fullRecords` array; use `fullRecords[0].metadata_product` and `fullRecords[0].metadata_sourceCategory` only for simplicity. If a rule fires and a signal is generated from a source, that source is contributing to detection coverage.

- **Insights** — groups of signals around an entity, generated when the total severity in a time window crosses a threshold. Insight-creation audit events are stored in `_index=sumologic_system_events _sourcecategory=cseinsight insightcreated`.

This methodology (record → signal → insight) means insights only surface for the most significant, well-contextualized events. Run this query over 14 days for a fuller picture, then map the signal and rule names in the output to infer the likely vendor or product per insight (insights do not carry vendor or product directly):

```sql
_index=sumologic_system_events _sourcecategory=cseinsight insightcreated
| json field=_raw "insight.description" as description
| json field=_raw "insight.riskScore" as riskscore
| json field=_raw "insight.severityName" as severityname
| json field=_raw "eventName"
| json field=_raw "insightIdentity.readableId" as insightid
| json field=_raw "insight.status" as status
| json field=_raw "insight.name" as name
| json field=_raw "insight.entityType" as entitytype
| json field=_raw "insight.entityValue" as entityvalue
| json field=_raw "insight.tags" as tags
| json field=_raw "insight.severity" as severity
| json field=_raw "insight.confidence" as confidence nodrop
| json field=_raw "insight.signals" as signals
| json field=_raw "insight.created" as created
| json field=_raw "insight.assignee" as assignee nodrop
| json field=_raw "insight.resolution" as resolution nodrop
| sort _messagetime
| max(_messagetime) as _messagetime, count, first(status) as status, first(resolution) as resolution, first(assignee) as assignee, first(signals) as signals, first(tags) as tags, max(riskscore) as riskscore, first(eventname) as eventname, first(severity) as severity, first(severityname) as severityname, first(confidence) as confidence by created, insightid, name, entitytype, entityvalue
| parse regex field=tags "\"(?<tag>[^\":,]+:[^\",:]+)\"" multi nodrop
| values(tag) as tags, count by created, _messagetime, insightid, name, eventname, entitytype, entityvalue, status, severity, severityname, confidence, riskscore, signals, assignee, resolution
| replace(signals, ",{\"id\":", "\n{\"id\":") as signals
| parse regex field=signals "(?<signal>\{\"id\":\"[^\r\n]+\})" multi
| json field=signal "id" as signal_id nodrop
| json field=signal "created" as signal_created nodrop
| json field=signal "name" as signal_name nodrop
| json field=signal "summary" as signal_summary nodrop
| json field=signal "severity" as signal_severity nodrop
| json field=signal "ruleId" as ruleid nodrop
| json field=signal "ruleName" as rulename nodrop
| concat(ruleid, " ", rulename, " sev:", signal_severity) as r
| sort insightid asc, signal_created asc
| concat(signal_created, "\t", signal_severity, "\t", signal_summary) as sig_blob
| count_distinct(signal_id) as sig_count, first(signal_id) as sig_id_first, first(signal_created) as sig_first_time, last(signal_created) as sig_last_time, last(signal_id) as sg_id_last, count_distinct(signal_id) as signals, values(sig_blob) as signal_timeline, values(r) as rules by created, _messagetime, insightid, name, riskscore, severityname, entitytype, entityvalue, confidence, tags
| num(riskscore) as riskscore
| sort insightid asc
| fields -_messagetime
```

- **`datavolume_with_tier`** — ingest volume by `_sourcecategory` and `tier`. `tier = CSE` (for tiered accounts) or `FlexSecurity` (for Flex accounts) indicates that the sourcecategory is routed to Cloud SIEM, either fully or partially.

```sql
_index=sumologic_volume _sourceCategory=sourcecategory_and_tier_volume
| parse regex "(?<data>\{[^\{]+\})" multi
| json field=data "field","dataTier","sizeInBytes" as sourceCategory, dataTier, bytes nodrop
| sum(bytes/1Gi) as gbytes by sourceCategory, dataTier
| sort gbytes desc
```

## Telemetry category taxonomy

Match observed `metadata_vendor`/`metadata_product` values against representative products. This is not exhaustive; use judgment for unlisted vendors.

Status values:

- **Missing** — zero matches
- **Partial** — low-volume or single-vendor coverage
- **Full** — multi-vendor, consistent volume

| Category | Representative vendors/products |
| :---- | :---- |
| EDR | CrowdStrike, SentinelOne, Microsoft Defender for Endpoint, Carbon Black, Cybereason |
| Firewall / IDS-IPS | Palo Alto, Fortinet, Cisco (ASA/Firepower), Check Point, Suricata, Snort |
| WAF | Cloudflare, F5, Imperva, AWS WAF, Akamai |
| Email security | Proofpoint, Mimecast, Microsoft Defender for Office 365, Abnormal Security |
| OS logs | Windows Event Log, Sysmon, Linux auditd/syslog, macOS unified logs |
| Identity | Okta, Microsoft Entra ID / Azure AD, Active Directory, Ping Identity, Duo |
| Cloud audit | AWS CloudTrail, Azure Activity Log, GCP Audit Log, Microsoft 365 Management Activity, Kubernetes audit logs |
| DNS / Network / Proxy (secondary) | Zscaler, Netskope, Infoblox, VPC/NSG flow logs |
| Vulnerability management (secondary) | Tenable, Qualys, Rapid7 |

## Analysis steps

1. **Record coverage** — query `sec_record_*`, aggregate by `metadata_vendor`, `metadata_product`, and `objectClassification`; map to the taxonomy; capture counts per vendor or product.
2. **Signal coverage** — query `sec_signal`, aggregate by `fullRecords[0]` vendor/product and rule name or ID; capture signal counts and distinct rule counts per category.
3. **Insight coverage** — run the insight query above over 14 days, then map signal and rule names in the results to the taxonomy to infer which categories are producing correlated insights.
4. **Ingest routing check** — run the `datavolume_with_tier` query above, then:
   - Sourcecategories with `tier` in (`CSE`, `FlexSecurity`) are already routed; note whether the volume looks partial or complete for that source.
   - Sourcecategories with meaningful volume, no `CSE`/`FlexSecurity` tier, and a name suggesting a security source (for example `waf`, `edr`, `fw`, `vpn`, `dns`, `proxy`, `okta`, `auditd`, `cloudtrail`, `o365`, `azure`, `gcp`) are strong forwarding candidates.
5. **Gap inference** — for taxonomy categories with weak or absent record or signal presence, infer likely gaps from the vendor mix seen elsewhere (for example, an AWS-heavy tenant with no GuardDuty or CloudTrail findings, or Okta identity logs but no EDR on the same hosts).
6. **Sanity check** — before reporting a category as Missing, confirm the query did not fail or use a misspelled field or index; note explicitly if the query failed rather than returned true zero results.

## Report structure

1. **Executive summary** — 3-5 sentences summarizing overall posture, the most critical gap, and the most urgent forwarding fix.
2. **Scorecard** — one row per taxonomy category, scored using the maturity scale below:

   Maturity scale (0-4):

   | Score | Meaning |
   | :---- | :---- |
   | 0 | No telemetry — nothing lands |
   | 1 | Collected — data arrives, but no detections are attached |
   | 2 | Parsed and mapped — normalized to schema |
   | 3 | Detections active — rules are firing and tuned |
   | 4 | Correlated — signals join across categories into insights |

3. **Coverage by category** — table with columns: Category | Vendor/Product | Records (24h) | Signals (24h) | Rules mapped | Status (Full/Partial/Missing)
4. **Sourcecategories not reaching SIEM** — table with columns: Sourcecategory | 24h volume | Suspected source type | Why it's a candidate
5. **Gaps and recommendations** — for each Missing or Partial category: likely cause, suggested product or source to close the gap, and priority (High/Med/Low) based on the technology stack evident elsewhere
6. **Notes and assumptions** — include inferred versus observed conclusions, and note any queries that failed instead of returning true zero results
