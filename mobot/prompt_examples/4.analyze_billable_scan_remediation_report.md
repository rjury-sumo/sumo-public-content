# Billable Scan Remediation Report

You are a Sumo Logic administrator analyzing billable scan usage in the account.

## Step 1: Determine the account type

First, determine the account type using the following query for a -15m range:

```sql
_view="sumologic_volume" _sourcecategory=view_and_tier_volume
(continuous or infrequent or flex) | limit 10000
| parse regex "dataTier\":\"(?<tier_type>[A-Za-z]+)" multi
| values(tier_type) as types | if(types matches /Flex/, "Flex", "Tiered") as account_type
```

## Step 2: Identify the top billable scan users

Use the following query to determine the top billable scan users in the last 7 days.

### Variant A

Run Variant A and identify users where `scan_gb_billable > 1000 GB`. Ignore the long tail.

Use only one of the following line 2 variants, because an invalid match can create very poor search performance when matching the wrong account type:

- For legacy CloudFlex accounts with infrequent logs: `analytics_tier=*infrequent*`
- For Flex customer accounts: `analytics_tier=*flex*`

```sql
_view=sumologic_search_usage_per_query
analytics_tier=*infrequent*  // Flex accounts only: analytics_tier=*flex*
// sum data_scanned_bytes gives total scan across all tiers
// scanned_bytes_breakdown_by_metering_type provides per-tier scan
// billable search types: Tiered Customer = Infrequent only; Flex Customer = Flex only
| json field=scanned_bytes_breakdown_by_metering_type "Infrequent" as scan_inf_billable nodrop
| json field=scanned_bytes_breakdown_by_metering_type "Flex" as scan_flex_billable nodrop
| if(isnull(scan_inf_billable), 0, scan_inf_billable) as scan_inf_billable
| if(isnull(scan_flex_billable), 0, scan_flex_billable) as scan_flex_billable

| scan_inf_billable + scan_flex_billable as scan_bytes_billable
// Variant A: use this high-level aggregation for per-user billable scan stats
| count as searches, sum(data_scanned_bytes) as total_bytes, sum(scan_bytes_billable) as scan_bytes_billable by user_name
| sort scan_bytes_billable
| scan_bytes_billable / 1Gi as scan_gb_billable
| total scan_gb_billable as tgbb
| 100 * (scan_gb_billable / tgbb) as pct_of_billable_scan
```

## Step 3: Drill down by user and scope pattern

For each user above the threshold, run Variant B below with a filter for that user.

Group results by the dominant scope pattern, defined as the same `_sourceCategory` plus the same keyword theme.

Report only the top 5 scope patterns per user by total `scan_gb_billable`, not individual query rows.

Use only one of the following line 2 variants, for the same reason noted above:

- For legacy CloudFlex accounts with infrequent logs: `analytics_tier=*infrequent*`
- For Flex customer accounts: `analytics_tier=*flex*`

```sql
_view=sumologic_search_usage_per_query
analytics_tier=*infrequent*  // Flex accounts only: analytics_tier=*flex*
// sum data_scanned_bytes gives total scan across all tiers
// scanned_bytes_breakdown_by_metering_type provides per-tier scan
// billable search types: Tiered Customer = Infrequent only; Flex Customer = Flex only
| json field=scanned_bytes_breakdown_by_metering_type "Infrequent" as scan_inf_billable nodrop
| json field=scanned_bytes_breakdown_by_metering_type "Flex" as scan_flex_billable nodrop
| if(isnull(scan_inf_billable), 0, scan_inf_billable) as scan_inf_billable
| if(isnull(scan_flex_billable), 0, scan_flex_billable) as scan_flex_billable
| scan_inf_billable + scan_flex_billable as scan_bytes_billable
// Variant B — drill-down (add user filter above before running)
| parse regex field=query "(?s)^(?i)(?<scope>[^\|]+)" nodrop
| (query_end_time - query_start_time) as time_range_ms
| count as searches, sum(data_scanned_bytes) as total_bytes, sum(scan_bytes_billable) as scan_bytes_billable, avg(scanned_partition_count) as avg_scanned_partitions, avg(time_range_ms) as avg_time_range_ms by user_name, query_type, scope, query
| sort scan_bytes_billable
| scan_bytes_billable / 1Gi as scan_gb_billable
| total scan_gb_billable as tgbb
| 100 * (scan_gb_billable / tgbb) as pct_of_billable_scan
```

## Step 4: Classify root cause

Classify each user's root cause as exactly one of the following:

- (A) FULL-ESTATE SCOPE — `avg_scanned_partitions > 50`, with no partition or index scoping
- (B) COLLATERAL DAMAGE — `avg_scanned_partitions = 1`, but the partition contains high-volume unrelated sources
- (C) EXCESSIVE TIME RANGE — query time range is disproportionate to the data needed
- (D) REPEATED AUTOMATION — Search API queries run with `_dataTier=All` at high frequency

## Step 5: Partitioning review for collateral-damage cases

Only if the classification is (B) and `scan_gb_billable > 5000 GB`, run this partition composition query for the last 60 minutes to minimize scan cost:

```sql
_index=<partition>
| sum(_size) as bytes by _sourceCategory
| sort bytes
```

Check whether high-volume sources in the partition are collateral to the user's actual search target. Use a similar query scoped to the target log source scope to determine what percentage of the partition size the target logs represent.

If there are large log sources unrelated to the search use case, or if the target logs are a very small percentage of the partition size, re-partitioning is a strong recommendation. Consider the following actions:

- Move a few very large log sources to another partition to reduce partition size for the current scope
- Create a new "high value, low size" partition for the target log sources to support high-search-volume use cases at lower cost
- For tiered customers, if the log size is relatively small and the search volume or use case is high, consider promoting this log source to a continuous partition where billing is mostly front-loaded for ingest and search is effectively free

## Final output requirements

Output the following and nothing more:

1. A summary table with columns:
   - User
   - Searches
   - Billable Scan (GB)
   - % of Total
   - Root Cause Category
   - Recommended Fix
   - Est. Scan Reduction

2. For each user in the table, exactly:
   - One sentence describing the root cause
   - One sentence stating the recommended fix
   - The estimated % scan reduction that fix would achieve

3. If partitioning recommendations are in scope, suggest changes and reasoning, such as the size of log sources relative to the scoped partition size.

Do not include per-query breakdowns, raw query text, or intermediate data.
