# Infrequent Tier Candidate Analysis — Log Volume & Search Usage Profiling (Top 3 Sources)

================================================================================
LOG VOLUME → INFREQUENT TIER ANALYSIS PROMPT
================================================================================
Purpose: Identify source categories that are candidates for moving from
Continuous to Infrequent tier by cross-referencing log volume, log content
profile, and active search usage patterns. 

The goal is to identify opportunity for data tiering to infrequent for lower value, less frequently searches logs or subsets of logs.

Inputs required: None — all data is derived from queries run during the analysis.
Estimated run time: 10–20 minutes depending on account size and query latency.

Run all queries within a step in parallel where noted. Do not write the report
until all queries across Steps 1, 2, and 3 have completed.
================================================================================

================================================================================
STEP 1 — Top Source Categories by Volume (Continuous Tier, last 24h)
================================================================================

Run this query (last 24h):
```
  (_index=sumologic_volume) _sourcecategory=sourcecategory_and_tier_volume
  | parse regex "\{\"field\":\"(?<value>[^\"]+)\",\"dataTier\":\"(?<dataTier>[^\"]+)\",\"sizeInBytes\":(?<sizeInBytes>[^\"]+),\"count\":(?<count>[^\"]+)\}" multi
  | where dataTier matches "Cont*"
  | sum(count) as events, sum(sizeInBytes) as bytes by dataTier, value
  | bytes /1024/1024/1024 as gb
  | sort gb desc
  | limit 20
```
Identify the top 3 source categories by GB. These are the targets for the
rest of the analysis.

--------
KEYWORD DERIVATION — Identifying the best search term for each source path
--------

Before moving to Step 2, derive a search keyword for each of the top 3 sources. These are suggested approaches, if they don't work well for logs under review you may need to be flexible and try another strategy.

This keyword is used in Step 3 to find active searches that reference each source.

The goal is to find the shortest substring of the source category path that
is (a) unique enough to avoid matching unrelated sources in the search usage
index, and (b) specific enough to avoid false positives from partial matches.

Work through these strategies in order, stopping when you have a keyword
with acceptable specificity:

STRATEGY 1 — Try the last path segment first
  The final segment of the path is often the most specific.
  Check whether it appears in any OTHER top-20 source paths.
  If it is unique across the top-20 list, use it as the keyword.
  If it is a generic term that likely appears in many source paths
  (common examples of generic segments: "api", "app", "public", "worker",
  "service", "logs", "output", "default", "main", "data"), move to Strategy 2.

STRATEGY 2 — Walk backwards up the path until unique
  Take the last two segments together, then three, and so on, until the
  combined substring no longer appears in any other top-20 source path.
  Use the shortest combination that achieves uniqueness.
  This naturally handles cases where the final segment is generic but the
  parent segment provides the necessary disambiguation.

STRATEGY 3 — Anchor on the most semantically distinctive segment
  Scan all segments of the path and identify the one that is most likely
  to be a proper noun, service name, or product name — something coined
  specifically for this application rather than an infrastructure convention.
  Proper nouns, internal codenames, and product identifiers make the best
  keywords because they are unlikely to appear in unrelated source paths
  or query text by coincidence.
  Use this segment even if it is not the last one, if it is more distinctive
  than the trailing segments.

STRATEGY 4 — Handle ambiguous prefixes explicitly
  If two or more sources in the top-20 share a common prefix such that any
  keyword derived from one would also match the other, note the ambiguity
  explicitly before running the Step 3 query.
  In this case, run the query with the broader keyword to capture all matches,
  then filter the results manually: separate rows that reference the exact
  target source from rows that reference the overlapping sibling sources.
  Treat each group independently in the fidelity analysis.

STRATEGY 5 — Validate before committing
  Before running the full Step 3 query, do a quick sanity check:
  mentally scan the other top-20 source paths and ask whether the chosen
  keyword could plausibly appear in a query targeting a different source.
  If yes, tighten the keyword using Strategy 2 or 3.
  If the keyword is a very common English word or infrastructure term,
  always prefer a longer or more specific alternative.

FALLBACK — Zero results after Step 3
  If the chosen keyword returns zero rows from the search usage index,
  try progressively broader keywords by removing trailing path segments
  one at a time until results appear.
  If zero results persist after trying the top two or three path segments,
  document the source as having no detected active search usage and treat
  it as a strong Infrequent candidate — but flag it for confirmation with
  the owning team before moving, since absence of scheduled/monitor usage
  does not rule out ad-hoc workflows.

In all cases: document the keyword chosen for each source and the strategy
used to derive it, so the analysis is reproducible in future sessions.

STEP 2 — Log Profiling (run all sample queries in parallel, then driver queries)
================================================================================

For each of the top 3 sources, first run the sample query (2a) for ALL sources
in parallel, then determine the format and run driver queries (2b) in parallel.
These are suggested approaches, if they don't work well for logs under review you may need to be flexible and try another strategy for a different or novel log format.

--------
2a. Sample logs — run ALL 3 in parallel:

```
_sourceCategory="<SOURCE>" | limit 50
```

  From the sample output, classify each source into one of these formats:

  FORMAT A — Structured text: level token + dotted class name before " - "
    e.g. "2024-01-01 [58] INFO com.example.ClassName - message"
    e.g. "2024-01-01 [58] ERROR Namespace.Class - {json payload}"
    Signals: log level keyword followed by a namespaced/dotted identifier,
    then " - " separator. Common in: log4net (.NET), Log4j (Java), Logback.

  FORMAT B — Top-level JSON with a logger/context field
    e.g. {"@l":"Information","SourceContext":"Namespace.Class","@mt":"..."}
    e.g. {"level":"info","logger":"com.example.Service","message":"..."}
    e.g. {"log.level":"info","service.name":"my-svc","msg":"..."}
    Signals: _raw starts with "{". Has a recognisable logger/context key.
    Common in: Serilog (.NET), Log4j2 JSON, Logback JSON, Logrus (Go),
    Zap (Go), Winston (Node), structlog (Python), OTel log body.

  FORMAT C — Unstructured / access log / syslog
    e.g. "192.168.1.1 - - [01/Jan/2024] GET /path HTTP/1.1 200 1234"
    e.g. "Jan 01 12:00:00 hostname process[pid]: message text"
    Signals: no consistent class/logger field. Structured around IP, method,
    status code, or syslog hostname/process fields.
    Common in: nginx, Apache, IIS, AWS ALB/CloudFront, syslog.

  FORMAT D — Text prefix wrapping an embedded JSON blob
    e.g. "2024-01-01 [58] INFO ClassName - {"key":"val","log_message":"..."}"
    Signals: structured text line with a JSON object embedded after " - ".
    Common in: .NET apps using log4net + structured logging extensions.

  DECISION TREE — pick format after reading sample:
    _raw starts with "{"?                           → FORMAT B
    _raw has "LEVEL ClassName - {" pattern?         → FORMAT D
    _raw has "LEVEL dotted.Class.Name - " pattern?  → FORMAT A
    _raw looks like IP/method/status or syslog?     → FORMAT C
    None clearly match?                             → use FALLBACK (see below)

--------
2b. Volume drivers — run ALL 3 in parallel using the format identified in 2a:

  --- FORMAT A: Structured text with level + class ---
  (log4net, Log4j, Logback, Python logging, Ruby Logger, etc.)

```
_sourceCategory="<SOURCE>"
| parse regex "(?:TRACE|DEBUG|INFO|WARN(?:ING)?|ERROR|FATAL|CRITICAL)\s+(?<logger>\S+)" nodrop
| where !isNull(logger)
| count by logger
| sort by _count desc
| limit 20
```

  --- FORMAT B: Top-level JSON with logger/context field ---
  (Serilog, Log4j2 JSON, Logback JSON, Logrus, Zap, Winston, structlog, OTel)

  Scan the sample output field names first to identify the right logger key,
  trying these candidates in order:
    "SourceContext"   → Serilog (.NET)
    "logger"          → Log4j2 JSON, Logback JSON, Python structlog
    "logger_name"     → Logback JSON (alternate)
    "log.logger"      → ECS (Elastic Common Schema)
    "service.name"    → OTel resource attribute
    "component"       → k8s/OTel pipelines
    "caller"          → Zap (Go)
    "module"          → Python structlog alternate

  Then run:
```
_sourceCategory="<SOURCE>"
| json field=_raw "<FIELD_NAME>" as logger nodrop
| where !isNull(logger)
| count by logger
| sort by _count desc
| limit 20
```

  If no single logger field dominates, group by message template instead:
```
_sourceCategory="<SOURCE>"
| json field=_raw "@mt" as msg_template nodrop
| json field=_raw "message_template" as msg_template nodrop
| where !isNull(msg_template)
| count by msg_template
| sort by _count desc
| limit 20
```

  --- FORMAT C: Unstructured / access log / syslog ---

  HTTP access log variant (nginx, Apache, IIS, ALB, CloudFront):
```
_sourceCategory="<SOURCE>"
| parse regex "(?<method>GET|POST|PUT|DELETE|PATCH|HEAD)\s+(?<uri>\S+).*?\s(?<status>[2345]\d{2})\s" nodrop
| if (isNull(status), "unknown", status) as status
| count by status, uri
| sort by _count desc
| limit 20
```

  Syslog variant:
```
_sourceCategory="<SOURCE>"
| parse regex "^\S+\s+\S+\s+\S+\s+(?<process>\S+)\[" nodrop
| where !isNull(process)
| count by process
| sort by _count desc
| limit 20
```

  --- FORMAT D: Text prefix + embedded JSON ---

```
_sourceCategory="<SOURCE>"
| parse regex "- (?<json>\{.+\})\s*(?:\[|$)" nodrop
| json field=json "<FIELD_NAME>" as logger nodrop
| where !isNull(logger)
| count by logger
| sort by _count desc
| limit 20
```

  Substitute <FIELD_NAME> with the logger key identified from the sample
  (e.g. "log_message", "ClassName", "SourceContext").

  --- FALLBACK: Format unclear or above queries return < 5 distinct values ---

  Run all three and use whichever gives the most useful grouping:

```
// 1. Log level distribution
_sourceCategory="<SOURCE>"
| parse regex "(?<level>TRACE|DEBUG|INFO|WARN(?:ING)?|ERROR|FATAL|CRITICAL)" nodrop
| if (isNull(level), _loglevel, level) as level
| count by level | sort by _count desc
```

```
// 2. Volume by host (is volume concentrated on specific instances?)
_sourceCategory="<SOURCE>"
| count by _sourcehost | sort by _count desc | limit 20
```

```
// 3. Message signature clustering (first 80 chars as a fingerprint)
_sourceCategory="<SOURCE>"
| parse regex "^(?<sig>.{0,80})" nodrop
| count by sig | sort by _count desc | limit 20
```

STEP 3 — Search Usage & Scope Fidelity (run all 3 in parallel, last 7 days)
================================================================================

Use the keyword derived for each source in Step 1. Run all 3 in parallel.

```
_index=sumologic_search_usage_per_query
| where query matches "*<KEYWORD>*"
| parse regex field=query "^(?<scope>[^\|]+)"
| trim(scope) as scope
| count as executions by scope, query_type, content_name, user_name
| sort by executions desc
```

--------
For each search result, classify scope fidelity:

  🟢 EXACT     — _sourceCategory="path/to/source" (quoted, no wildcard)
                 Scans only this source. Highest confidence for Infrequent safety.

  🟡 WILDCARD  — ```path/to/source*``` or ```path/*/source``` or ```*/env/source*```
                 Matches this source AND siblings under the same path prefix.
                 Check whether siblings are also high-volume — a wildcard search
                 spanning a moved source + a Continuous sibling will still work
                 but will only scan the Continuous sibling going forward.

  🟠 MULTI     — (_sourceCategory=A OR _sourceCategory=B)
                 Shared scope across 2+ sources. Moving one source to Infrequent
                 means this search will scan cross-tier — still works but incurs
                 Infrequent scan costs on the moved portion.

  🔴 BROAD     — No _sourceCategory scoping, source appears only in a comment,
                 or scope is a top-level wildcard that matches everything.
                 Source contribution to this search is incidental.

--------
For each search, also assess keyword filtering:

  KEYWORD-FILTERED — scope includes one or more specific literal strings,
    error messages, class names, or field values alongside the source filter.
    → SAFE on Infrequent: literal pre-filters before scan, cost is low.

  BROAD SCAN — source category is the only filter, with no keyword to
    pre-filter on. Includes: | count with no keyword, | timeslice with no
    keyword, | where _loglevel = "X" with no additional string filter.
    → BLOCKER for Infrequent: scans full source on every execution.

  Always flag as BLOCKERS regardless of keyword filtering:
    - MissingData monitors (require continuous log presence detection)
    - Healthcheck searches that assert log volume > 0 (same reason)
    - Any search with execution frequency > 1000/week AND no keyword filter

--------
Summarise per source:

  | Fidelity     | Searches | Executions/wk | Keyword-filtered |
  |--------------|----------|---------------|------------------|
  | 🟢 Exact     |          |               | N of N           |
  | 🟡 Wildcard  |          |               | N of N           |
  | 🟠 Multi     |          |               | N of N           |
  | 🔴 Broad     |          |               | N of N           |

  Blockers: list each blocking search with content_name, query_type,
  executions/wk, why it blocks, and suggested remediation:
    - Broad count/healthcheck → replace with metrics-based monitor
    - MissingData monitor → replace with infrastructure health check
    - High-frequency broad scan → add a keyword filter to the query scope

  Infrequent verdict:
    ✅ SAFE        — no blockers; all searches keyword-filtered
    ⚠️ CONDITIONAL — blockers exist but have clear remediations
    🔴 BLOCKED     — blockers with no straightforward remediation

ANALYST NOTES
================================================================================

Query execution:
  - Run Step 2a sample queries for all sources in parallel.
  - Determine formats from samples, then run Step 2b driver queries in parallel.
  - Run all Step 3 search usage queries in parallel.
  - Use 7-day windows for Step 3 — captures daily, hourly, and weekly schedules.
    30-day windows time out on large accounts; 24h windows miss weekly schedules.
  - The search usage index is: _index=sumologic_search_usage_per_query
    (not _index=sumologic_audit_events — that index does not contain query text).

Infrequent tier compatibility rules:
 - strongest infrequent candidates have only ad-hoc search workloads ie: no dashboard, schedule search, monitors, views.
  - Keyword-filtered searches (specific literal strings) and fer fields → work on Infrequent ✅
  - Log-level-only filters (| where level = "Error") → work but scan full source ⚠️
  - Broad count/volume searches (| count with no keyword) → blocker 🔴
  - MissingData monitors → always a blocker 🔴 (require continuous presence)
  - Healthcheck searches asserting log volume > 0 → blocker 🔴
  - Infrequent searches must be scoped by ```_datatier=``` or ```_index=<infrequent index>```  so moving logs to infrequent removes them from the default search scope →
    can functionality break existing searches that targeted only by sourcecategory / keyword, as search matches less events 
  - if blocker is aggregate e.g golden signals, check if a suitable alterative is using metrics based evaluation. e.g request count, 5xx count. Logs add the most value for detailed troubleshooting not high level signal aggregation, except for custom or transaction use cases. ⚠️

Wildcard source category notes:
  - A wildcard scope may cover multiple sub-sources under the same path prefix.
  - Before moving any source, check whether siblings exist under the same prefix
    and whether those siblings are also candidates or must stay on Continuous.
  - If siblings must stay on Continuous, wildcard searches will continue to work
    but will no longer pick up / scan the moved source on Infrequent only siblings on Continuous.

Zero search usage sources:
  - If a source has no search usage in 7 days, it is a strong candidate.
  - Always recommend confirming with the owning team before moving — absence of
    scheduled/monitor usage does not rule out ad-hoc debugging workflows or
    downstream dependencies (data forwarding rules, scheduled views, field
    extraction rules) that reference the source category.

Sources to investigate before moving to Infrequent:
  - Any source with active MissingData monitors
  - Any source referenced by a scheduled view or partition routing rule
  - Any source used as input to a data forwarding rule. Check for the source's
    partition/index name to identify forwarded sources:
    ```
    _index=sumologic_system_events _sourceCategory=dataForwarding
    ```
