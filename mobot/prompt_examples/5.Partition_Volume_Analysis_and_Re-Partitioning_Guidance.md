# Partition Volume Analysis and Re-Partitioning Guidance

You are a Sumo Logic administrator reviewing a partition to optimize search use cases versus the default `sumologic_default` partition.

Best practice is to keep partitions well scoped and aligned to specific search use cases. If the default partition grows large, creating new partitions to route logs to specific partitions will reduce data scanned.

- In tiered customer environments, this improves performance and can reduce ingest cost if large logs or subsets of large logs are moved to an infrequent partition.
- In Flex customer environments, the default partition is typically part of the default search scope, so its size directly impacts the cost of searches run with default scope.

Run this search for the last 3 hours using `receipttime`, and perform an analysis of the size breakdown of categories in the partition.

## Objectives

- Show the breakdown of large-volume contributors
- Identify whether there are single categories or similarly named categories that are driving large volumes
- Recommend which categories could be moved to named partitions

## Volume analysis and log profile within a partition

Use the query below to find the top three volume-driving categories:

```sql
_index=sumologic_default
| sum(_size) as bytes, count as events by _sourcecategory
// optional: if there are too many categories and a high-level view is needed,
// you can run a subset analysis by adding _sourcecategory=*pattern* to the search scope.
// use this approach only if necessary, as it makes the search execute much slower
// | if(length(_sourcecategory)>30,concat(substring(_sourcecategory,0,30),"*"),_sourcecategory) as _sourcecategory
// | sum(bytes) as bytes, sum(events) as events, count as categories by _sourcecategory
| sort bytes
| bytes / 1Gi as gb
| total gb as total_gb_all
| 100 * (gb / total_gb_all) as gb_percent
```

## Then profile the most relevant categories

Use scoped searches against each high-volume category to:

1. Sample the logs to understand the log format and schema, and map this to the collection metadata to understand the ingest pipeline
2. Analyze the logs by common facets such as log level, collector, source, error message, or other known fields to understand whether certain log event types are driving high volume within the source

### Example search to profile metadata for a log source

```sql
_sourcecategory=foo  // from the previous top-X step
| sum(_size) as bytes, count as events by _view, _sourcecategory, _collector, _source
```

### Example search to profile raw events

```sql
_sourcecategory=foo  // from the previous top-X step
| limit 50
```

### Example search to estimate size by discovered fields

```sql
_sourcecategory=foo  // from the previous top-X step
// optional parsing operators
// | json "foo" as foo
// | parse ...
// | parse regex ...
// use parsed fields to analyze and report volume drivers
| sum(_size) as bytes by _loglevel, logger | sort bytes | limit 50
// | sum(_size) as bytes by cs_host, cs_uri_stem | sort bytes | limit 50
// | sum(_size) as bytes by errorcode, errordescription | sort bytes | limit 50
```

## Re-partitioning recommendations

Recommend a data-tiering strategy for the log source by investigating:

- Data-tiering candidates
- Subsets of log data that are high-volume drivers
- Field-based statements and partition routes that could support a more complex routing scheme

## Deliverable

Provide a concise assessment covering:

- Top volume contributors in the partition
- Whether a few categories or similar category groups are dominating the volume
- Which categories are good candidates to move into named partitions
- A short recommendation for how to route or tier the data to reduce scan cost and improve search performance
