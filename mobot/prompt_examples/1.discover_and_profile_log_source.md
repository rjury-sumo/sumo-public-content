# Discover and Profile a Log Source

For the log source: `[LOG SOURCE NAME]`

## Goal

Create a concise but comprehensive profile of this log source covering its collection pipeline, schema, and use cases.

## Phase 1 — Source discovery

Use discovery tools such as key-value pair stats, related queries, and user query history to identify the source expression(s) for this log source. Look for `_sourceCategory`, `sumo.datasource`, `_source`, and any other relevant key-value pairs.

If you cannot confidently identify a source expression, stop and ask me before proceeding.

Do not run open-ended wildcard searches such as `*`; these are slow and can incur scan charges.

## Phase 2 — Log sampling

Once the source expression is confirmed, sample recent logs to understand the format and schema:

```sql
<source_expression>
| limit 20
```

Use only recent time ranges, ideally between `-15m` and `-1h` maximum. If no logs are found in `-15m`, try `-1h`; if nothing is still found, stop and ask me before proceeding. Do not expand beyond `1h` without checking with me.

## Phase 3 — Partition and metadata profile

Run the following to identify which partition(s) these logs live in and the key metadata values:

```sql
<source_expression>
| limit 1000
| count by _view, _sourcecategory, _collector, _source, _sourcename
| if(isempty(_view), "sumologic_default", _view) as partition
| fields -_view
```

Rules:

- Use `_view` to identify the partition, not `_index` or `_dataTier` because those fields do not exist in log records.
- If `_view` is empty, the log is in `sumologic_default`.
- Partition billing tier (Continuous, Infrequent, or Flex) cannot be read from log fields; note it as "check partition config" unless you can determine it from context.

## Phase 4 — Schema and field profiling

Identify the log format (plain text, JSON, CEF, etc.) and the key fields. For structured logs, extract the top field names and representative values. For unstructured logs, identify the parsing pattern. Keep queries fast:

```sql
<source_expression>
| limit 1000
| <parse or json auto>
| count by <key_field_1>, <key_field_2>
```

Select 2-3 high-value fields per query. Run targeted field aggregation queries rather than one large broad query.

## Phase 5 — Collection pipeline

Check the OTel or Installed Collector details to understand how logs are collected:

- Collector type (OTel / Installed / Hosted)
- Collector name and version
- Alive status
- Relevant collector tags such as `deployment.environment` or `host.group`
- Source file path or API endpoint being collected

## Phase 6 — Use case discovery

Check existing saved content that references this log source; these are high-fidelity signals for how the logs are actually used:

1. Related queries — search for customer saved queries and dashboards that reference this source
2. Dashboards — search the dashboard library for the log source name
3. Monitors — check for monitors referencing this source category
4. Scheduled searches — check audit and content for scheduled searches

Summarize what use cases are already implemented versus what is possible based on the schema.

## Phase 7 — Deliver the report

Produce a concise report with the following sections:

### Collection pipeline

- Collector type, name, version, host, and alive status
- What is being collected (file path, API endpoint, etc.)
- Collection method (filelog receiver, HTTP source, etc.)
- Notable collector tags or configuration

### Metadata and partitions

Table columns:

- Partition name
- Billing tier (or "check config")
- `_sourceCategory`
- `_source`
- `_collector`
- `_sourcename`
- Content type
- Any OTel resource attributes (for example `os.type`, `host.name`, `deployment.environment`)

### Log format and schema

- Format: plain text / JSON / CEF / other
- Parse pattern (for unstructured logs) or top JSON fields (for structured logs)
- Key fields table: field name | type | example value | description
- Sample raw log line

### Common search use cases

Provide 3-5 example queries with brief descriptions, using the confirmed source expression and confirmed field names only. Do not invent field names.

### Saved content

Table of monitors, dashboards, and scheduled searches that reference this log source. If none exist, state that explicitly.

### Observations and recommendations

- Any gaps, such as no saved content for a production source
- Whether a collector upgrade is available
- Whether the environment is single-host or fleet-based
- Suggested next steps
