# SIEM Parsing and Mapping Failure Report

> Prompt to copy and use:

Generate a Cloud SIEM Parsing and Mapping Failure Report for the last 7 days.

Use `_index=sec_record_failure` to query the SIEM failed-records index. The report should be concise and structured as follows:

## 1. Scope and volume summary

Query the total failed-record count over the last 7 days. Break it down by failure category:

- Parse failures (`reason` contains "Parsers")
- Mapping failures (`reason` contains "No mapping matched")
- No parser matched ("Log was not parsed by any parser")
- No mapper defined ("No mapper is defined" / "No fields mapped")

Show counts and percentage of total for each category.

## 2. Top 5 problems with suggested fixes

Run this query to identify the top 5 failure reasons by volume:

```sql
_index=sec_record_failure*
| count by %"fields.reason"
| sort _count desc
| limit 5
```

For each of the top 5 results, present it as a bullet point with:

- Problem: the failure reason (parser name + error message)
- Source: the `metadata_sourceCategory` and `metadata_vendor` / `metadata_product` most associated with the failure (use the detailed breakdown query below)
- Volume: record count
- Suggested Fix: based on the failure reason pattern, suggest one of the following:
  - Parser format mismatch (for example, "parse failed" or "none of the transforms in cascade") → Sample 3-5 raw log messages from the failing `_sourceCategory` and examine their structure. Check whether the log format (for example CSV field count, syslog header, or JSON structure) matches what the parser expects. Consider whether a log format version change has occurred (for example, a PAN-OS upgrade changed the CSV column layout).
  - Missing required field (for example, "no value found in required transform target field") → The parser expects a specific JSON key (for example `message.data.logName`) that is absent. Sample the raw messages and check whether the field exists under a different path or is null. The source may be sending a different log subtype (for example, structured vs. unstructured GCP logs).
  - No mapping matched → A parser successfully ran, but no SIEM mapper covers this `eventId`. Check whether a custom mapper needs to be created for this vendor/product/eventId combination, or whether the log source should be excluded from SIEM processing.
  - Log not parsed by any parser → No parser is assigned or matched. Check the source `_sourceCategory` in the SIEM collection pipeline and confirm that a parser is configured and that the log format matches the parser's expected input.

## 3. Sample raw messages for the top 2 problems

For the #1 and #2 failure reasons, retrieve the `metadata_sourceMessageId` of a recent failed record, then use a subquery to pull the original raw log from the source `_sourceCategory`. Display 2-3 sample messages and comment on:

- What log structure is present (JSON, syslog, CSV, or plain text)
- What field or pattern the parser was expecting versus what was found
- Whether the log appears to be from the correct source type for the assigned parser

Use this pattern to retrieve the original messages:

```sql
_sourceCategory=<failing_sourceCategory>
  [subquery: _index=sec_record_failure* metadata_sourceCategory=<failing_sourceCategory>
  | count by metadata_sourceMessageId
  | metadata_sourceMessageId as _messageId
  | compose _messageId maxResults=5]
| limit 5
```

## 4. Collection pipeline context

For the top 2-3 failing source categories, check the collection pipeline:

- Identify the collector and source type (Installed / Hosted / OTel)
- Note the collector version and whether it is online
- Flag any sources with `metadata_vendor=UNKNOWN` — this indicates the log reached SIEM but the parser could not identify the vendor, which may mean the wrong parser is assigned or the source-category routing is misconfigured

Keep the final report to one screen. Lead with the volume summary, then the top 5 bullets, and close with 2-3 sample log observations and collection notes.
